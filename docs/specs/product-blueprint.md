## 一、拍板人期望的流程（原话，不改一字）

> 1. 用户安装了这个 Skills 之后，可以上传自己的简历。
> 2. 我们读取他的简历，并根据简历内容向他提问（比如针对每个 application 需要的不同基础信息）。
> 3. 结合简历给他生成一些定制化的问题，让他回答。
> 4. 在他回答完之后，我们总结这些回答，生成一个用户画像。
> 5. 询问他想找什么样的工作，然后根据画像帮他寻找合适的工作并进行投递。

补充拍板：**不做独立看板**——总结做成 skill 跑完后自然给出的一份 summary。运行环境 = 在 Codex 里装好 skills 就能用。

## 二、5 步逐条现状判定

| 步 | 现状 | 差在哪 |
|---|---|---|
| 1 上传简历 | **门槛最高** | "上传"实际是要用户打一串绝对路径（`mrweirdo-onboard/SKILL.md:120`）+ 手动起调试模式 Chrome |
| 2-3 读简历后针对性提问 | **内核对，位置错** | 「从真实岗位表单反推 + 压缩」**确实实现了**（`shared/missing_field_questions.mjs:137-181`，带"压缩后必须覆盖全部原始类目、漏一个抛错"的硬校验，按去重岗位数排序）——但它只在投递**之后**触发。「结合简历定制化」**零实现**：问题措辞是 12 类写死的共用模板，与简历无关 |
| 4 生成用户画像 | **最完整的一步** | 基本符合预期 |
| 5 找岗并投递 | **坏了** | 41 天零投递；可投数量读数失真（见第四节） |
| —— | **拍板人最在意的「投了几家、几家回了」不在这 5 步里** | 回执测量从未运行过（见第四节） |

## 三、🔴 首要缺陷：主入口首跑必挂（已独立复验）

`mrweirdo-onboard/SKILL.md` 共 **9 处** 使用 `cd "$MRWEIRDO_REPO_ROOT"`，而该变量**从不被设置**。bash 里 `cd ""` 退出码为 0 且不换目录 → 第一条命令静默"成功"，第二条抛裸报错：

```
bash: scripts/preflight.sh: No such file or directory   （退出码 127）
```

**8 个次要技能**（ashby / lever / workday / icims / jobvite / handshake / smartrecruiters / confirm）**都写了兜底，唯独主入口漏了**。`shared/paths.mjs:18` 的注释还写着这个契约存在。

**这就是「没人真正上手试过、体感不好」的直接原因——按 README 操作的人走不到第二步。**

## 四、其余已确认的断点

1. **回执测量从没跑过**（不是坏了）：`confirmed_at` 唯一写入者是 `local_db.mjs:405 markConfirmed()`，唯一调用点是 `mrweirdo-confirm/SKILL.md:115`——只有手动敲命令才跑；生产代码零调用、测试零覆盖、无定时任务。同模式还命中 `outcome_status` / `followup_count`，即**主流程第 6 步（持续跟进）整段没落地**。报告把 `confirmed_total` 直接显示成 0，不区分「测过是 0」与「没在测」＝静默降级。
2. **可投数量失真的真因已修正**：看板 562 / 诊断 215 / 真队列 18。原判「字段只在跑批时刷新、重跑即可」**错误**——architect 实跑刷新程序（只算不写）结果放行 0 行、收回 1 行。真因是 `recompute_auto_apply_eligibility.mjs:81-83` 的守卫：打分记录缺 `recommended` 字段一律不放行，DB 实查 **244 行**是 2026-06 中旬打分提示词升级前的旧数据。**出路只有「重新打分」或「改守卫策略」二选一——这是取舍，不是 bug。**
3. **两处对外安全承诺在默认安装下不成立**：免责声明写的「约 25 家大公司默认跳过保护名额」——`paths.mjs:75-82` 找不到用户自建名单即返回空数组，安装脚本不生成该文件，**护栏对任何公司都不生效**；免责声明描述的「解析确认门」已在 2026-06-13 改版中拆除（`SKILL.md:231` 明写不等确认）。
4. **🔴 已核实（P1，上线前必修）：系统会替用户答关于他本人的事实问题，且答案可能是假的。** 实跑 `deriveWorkAuthAnswers()`（`answer_routing.mjs:173-181`）配出货的 `answer_bank.json`，喂 5 种档案（含**明确填了"未获授权"**与**字段全缺**）——**5 次全部输出 `Yes`**，当前配置下没有能力输出 `No`。根因不是漏判空，是**三态字段（是 / 否 / 没问过）被用真假判断读**：`false` 与 `null` 一起掉进默认分支，而默认值恰好是 `Yes`。
   - 三处默认原值：工作授权 `Yes`、硕士学位 `No`（`greenhouse_apply_driver.mjs:1569` 写死、根本不读档案）、退伍军人 `I am not a protected veteran`。
   - **反向错误**：用户**不需要**担保时 Ashby 会答"我需要担保"（同函数 `:175-177`），把美国公民标记成需担保，很多雇主直接刷。Greenhouse 同一件事写的是 `=== false ? 'No' : ...` 是对的——**两平台写法不一致，证明属疏漏而非设计**。
   - **历史取证：没找到答错的证据，但洗不清**。15 条 submitted 仅 1 条留字段级痕迹（2026-05-28，与档案真实值一致）；`feedback` 表只存"跳过时缺什么"、不存"填了什么"，180+ 条投递答了什么**已不可考**。
   - **守门人站错了队**：红线（`PRD-v3.md:230`）指定 `apply_gap_report.mjs` 的 `user_*` 分类为执行机制，而该分类器 `:137` 把 veteran / gender / race / disability / authorized-to-work **全判成"系统自动填"**——即使修好默认值，这些题也永远进不了"该问用户"清单。
   - **人口统计学答案不是用户答的**：真实档案的 `demographics.veteran_status` 与 `profile.template.json` 出厂默认**逐字节一致**，且引导流程无任何相关提问——代码分辨不出"用户说的"与"出厂预填"。
   - **为什么一路绿灯**：`test/answer_routing.test.mjs:75-89` 只覆盖 `true` 的两种情形，`false` 与缺失**零覆盖**。
   - **当前不着火**：41 天零投递；现有唯一用户 5 个默认值里 4 个碰巧与真实一致——**巧合，非机制保证**。
5. **`answer_bank.json` 是全体用户共用的一份**，还留着针对特定公司的硬编码条目——多用户场景下所有人答出去的话相同。

## 五、拍板人写过、但没被实现的需求

**「把上一轮卡住的字段沉淀成下一轮的前置问题、批量提前问」**——拍板人在 `docs/archive/HANDOFF-v2.2.0.md:336-339` 与 `shared/essay_profile.template.json:80-83` **写过两遍**。零件全在（`shared/apply_gap_report.mjs:407-417` 已在计算这份清单），**只差最后一根线没接**。接上即同时兑现期望流程的第 2、3 步。

**结论：这不是功能缺失，是接线缺失。**
