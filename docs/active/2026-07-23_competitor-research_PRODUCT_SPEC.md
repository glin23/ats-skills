# 竞品调研 — AI 自动求职 / 批量投递赛道（第一轮：公开搜索）

> 本轮只做公开网络搜索。拍板人后续提供的 GitHub 链接属第二轮，未包含在内。
> **能力边界（如实）**：本轮工具箱只有网络搜索，**没有网页抓取、没有命令行**。所有外部结论来自搜索结果摘要，我**没有真正打开过任何一个网页**，也没有注册、下载、提交任何东西。因此下文每条关键结论都标了来源等级，C 级的数字请当"方向参考"而不是"事实"。

## 0. 给拍板人的结论（一页，人话）

**一句话**：市场上「更快更多地批量投递」这条路，2026 年已经有人替我们撞过墙了——撞墙的还不止一个。我们该做的不是把这条路修得更快，而是把它修得**更准、更可信、更看得见结果**。

### 市场上主要有四种玩法

| 玩法 | 谁在做 | 谁点"提交" | 活得怎么样 |
|---|---|---|---|
| ① **帮你填表，你自己点提交** | Simplify Copilot、LinkedIn 自营 Apply Assistant、career-ops（开源） | 用户 | **最健康**。平台自己都下场做了 |
| ② **云端替你全自动投** | JobCopilot、LoopCV、AIApply、Resumly、Sonara | 服务商的服务器 | 有收入，但口碑普遍很差（退款纠纷、BBB F 级、Trustpilot 低分） |
| ③ **在你电脑上跑机器人** | LazyApply、AIHawk 及一堆开源 Easy-Apply bot | 你的浏览器 | **正在死**。AIHawk 已归档，LazyApply 退款纠纷成堆 |
| ④ **真人（或半真人）替你投** | ApplyPass、各类 reverse recruiter | 人 | **最赚钱**，$99–$4500/月，主流财经媒体在追着报道 |

**我们处在第 ③ 格**——最难看的那一格。但我们有一个别人没有的位置差：**我们不碰 LinkedIn 和 Indeed，只投企业自己的招聘系统（Greenhouse/Ashby/Lever），而且跑在用户自己的机器上**。第 ③ 格里死掉的那些，基本都是死在"在 LinkedIn 上跑机器人"和"投得多但没人回"这两件事上，这两件我们都有回避的余地。

### 最该学的三件事

1. **学 Simplify 的入口物**：它跟 Pitt 大学计算机社团合办的实习清单仓库 `SimplifyJobs/Summer2026-Internships` 有 **4.4 万 star**，每天更新——一个免费、学生天天用的东西，把人喂给它的产品。我们现在没有任何"免费也值得用"的入口，只有一个必须装 Node 24 + Chrome + Claude Code 才能跑的重家伙。
2. **学 Jobright 的细分定位**：一样是学生/应届向，融资 $7.7M（2025 年 6 月那轮有 Indeed 的风投参与），号称 52 万用户、约 $5M 年经常性收入。它证明"学生 + AI 匹配"这个细分是能起量的——但它赢在匹配和免费额度，不在投递条数。
3. **学 career-ops 的边界叙事**：这是跟我们**最像**的对手——开源、MIT、本地跑、跑在 Claude Code/Codex 这类 CLI 里、同样覆盖 Greenhouse/Ashby/Lever。它跟我们唯一的区别是它**明确宣布不替你点提交**，并把这句话做成了卖点。它的 star 数被各处引用（34k / 60.9k 口径都有，我核不实），但无论哪个数都比我们大两个量级。

### 最该避开的三个坑

1. **"投得更多"这个坑**。Wonsulting 官方博客自己写了一篇《我们为什么废掉了自动投递工具》——理由是投得多不等于面试多。AIHawk（2.96 万 star 的赛道明星）2026 年 5 月被作者归档。多个来源都指向"泛投回复率 2–3%，定制投递 7–18%"（这些数字是 C 级来源，别当真，但方向一致）。
2. **在别人的地盘上跑机器人**。LinkedIn 用户协议明文禁 bot，2023 年透明度报告把自动化列为限权首因；2026 年 3 月 LinkedIn 下架了自动化厂商 HeyReach 的页面。我们 README 里"永不自动化 LinkedIn/Indeed"这条红线是对的，**别回头**。
3. **静默地以用户的名义对外做错事**。这是我们自己的真实风险：我们刚发现系统"还剩多少能投"读数错了 14 倍、39 天空转不投——今天它静默地少做事，明天同样的缺陷可以让它静默地多做事。学生的名字投出去就收不回来，一次乱投是不可逆的。

### 一句反驳（详见 §10）

拍板人问的是"我们该怎么做得更好"。诚实回答是：**"更好地批量投递"这个命题本身正在贬值。** 已拍板的 P1（修读数缺陷 + 跑通一轮）**该做，且必须做**——不跑通我们连自己的回复率是多少都不知道。但请把它理解为"去拿数据"，不是"我们的战略就是投得多"。

## 1. Executive Summary

批量自动投递赛道在 2026 年已进入"机制分层、量价背离"阶段：靠**投递数量**定价的产品普遍口碑崩塌或退场（Sonara 倒闭后被收购、Wonsulting 主动废弃自研自动投递、AIHawk 归档、LazyApply/AIApply 差评与退款纠纷集中），而**辅助填表**（被 LinkedIn 自营收编）和**真人代投**（$1500/月量级、财经媒体热点）两端在增长。同时雇主侧开始反向加固（Greenhouse 与 CLEAR 合作做候选人身份核验）。

Mr. Weirdo Jobs 当前定位（学生向 · 本地跑 · 批量自动投 Greenhouse/Ashby/Lever）在**机制上**处于最危险的一格，但在**边界上**（不碰 LinkedIn/Indeed、数据不出本机、内置相关性门控与不实内容防线）恰好持有这一格里罕见的合规与信任资产。建议：不改变已拍板的 P1 执行顺序，但把对外叙事与后续路线图的主轴，从"投得多"改为"投得准 + 投得可信 + 跟得住"，并把"回复率"而非"投递条数"设为主指标。

## 2. Problem Statement（问题陈述与证据）

### 2.1 拍板人的原始问题

"看到过很多人做类似的项目，想法跟我一样"——他想知道别人怎么做的、我们该怎么做得更好。

### 2.2 三类证据

**证据一：自家实测数据（A 级，直接查库，来自父任务）**

| 指标 | 数值 |
|---|---|
| 岗位总数 | 950 |
| 够格（fit≥5）且从未投过 | 292 |
| 系统标记可投 | 20（读数错约 14 倍） |
| 历史已投 | 183 |
| `confirmed_at` 非空 | **0** |
| 最后一次投递 | 2026-06-14（至今 39 天零投递） |

**最关键的一行是 `confirmed_at` = 0。** 意思是：我们投出去 183 条，**一条回音都没有记录在案**。我们的主流程写着"投递报告 → 持续跟进直到拿 offer"，但漏斗的最后一格从来没亮过灯。这不只是一个 bug——它意味着**我们无法回答"我们的产品有没有用"这个问题**，而这恰恰是整个赛道正在被拷问的问题。

**证据二：赛道量化数据（来源等级见 §11）**

- LinkedIn 每分钟处理 1.1 万条投递，同比增长 45%，主要由 AI 投递工具推动（B 级：eWeek 报道）。
- 每个招聘岗位平均收到 242 条投递（C 级）；投递转面试比从 2016 年的 15.25% 掉到 2024 年的 3%（C 级）。
- 泛投回复率约 2–3%，定制投递 7–18%（C 级，多个互相抄写的来源，方向一致但数字不可信）。
- Wonsulting 自述：废弃自动投递功能的理由就是"投得多不等于面试多"（**A 级：厂商自己的博客**）。

**证据三：赛道"工单/口碑计数"（C 级，均为竞品 SEO 博客转述，我未打开原始评价页）**

- LazyApply：Trustpilot 低 2 分区间，1 星占比 >20%，退款需走信用卡拒付。
- AIApply：BBB 给 F 级、未认证、多条 2024–2026 投诉状态为"未回应"；$29/月套餐**不含**自动投递（要另买 credits，100 条实际约 $68）。
- Sonara：2024-02-01 因融资失败突然停服，用户被锁在自己的投递记录外面。后被 BOLD（Zety/LiveCareer 母公司）收购，2026 年是否真在运营，来源互相矛盾，**我核不实**。

### 2.3 真正的问题陈述

我们不缺"投递能力"，我们缺三样东西，而且缺的这三样恰好是这个赛道正在洗牌的三样：

1. **缺证据**——不知道自己投出去有没有用（`confirmed_at` = 0）。
2. **缺入口**——除创始人本人外没有真实用户，安装门槛（macOS + Node 24 + Chrome + Claude Code）把"面向大学生"缩窄成"面向会跑开发者工具的大学生"。
3. **缺叙事**——我们最强的资产（本地、不碰 LinkedIn、有刹车、不说谎）一条都没被讲成卖点，README 讲的是"能自动提交"，正好是市场上最跌价的那句话。

## 3. Personas（用户画像）

**P1 — 正在找实习的美国在校本科生（当前唯一被验证的画像，样本 n=1，就是创始人）**
- 要完成的任务（JTBD）：功能层 = 在一个季度里投够足量对口的实习岗；社交层 = 不想在同学面前显得"没在努力找"；情感层 = 想摆脱"每天填 30 遍同样的表"的无力感。
- 追问 5 Why 后的真实任务：他要的不是"投递 292 条"，是"**知道自己这一季有没有在推进**"。投递条数只是他能看见的唯一代理指标——因为回音这一格是黑的。

**P2 — 非技术背景的美国大学生（目标画像，尚未验证）**
- 当前装不上我们的东西。这是产品定位与产品现实之间最大的一道裂缝。

**⚠️ 诚实声明**：本轮**没有做任何一手用户访谈**。按 Mom Test 的标准，上面 P1 的 JTBD 拆解基于创始人自己的使用行为与已有反馈档案，**不是 3 个以上用户的饱和访谈**。P2 完全是假设。这是本次调研最大的证据缺口，已列入 Open Questions。

## 5. 失败案例与死因（本轮最有价值的部分）

**① Sonara — 死于烧钱模型，2024-02-01**
云端代投的先驱，突然停服，官方理由是没融到钱，用户被锁在自己的记录外面。后被 BOLD 收购。
**死因本质**：云端代投的成本结构是"每条投递都要我付服务器 + 模型钱"，而用户愿意付的钱按"月"计。量越大越亏，靠融资填。融资一停，产品当天死。
**对我们的意义**：我们的推理跑在用户自己的 Claude Code/Codex 会话里，**我们不为每一条投递付钱**——这是我们相对整个第 ② 格的结构性成本优势，而且是真实的、不是营销话术。

**② Wonsulting AutoApplyAI — 死于效果，自己动手废的**
厂商官方博客标题就是《我们为什么废掉了自动投递工具（以及什么更管用）》，理由直白：投得多不等于面试多，定制的简历 + 聚焦的目标，比海投更能提高面试率。
**这是本次调研里最硬的一条证据**——不是评测博主说的，不是竞品说的，是**做这门生意的人自己说自己这门生意不成立**。

**③ AIHawk — 死于生态反噬，2026-05 归档**
2.96 万 star 的赛道旗舰。搜索结果里的批评点集中在：这类工具把招聘方的收件箱冲垮（有招聘经理称单个岗位 24 小时收到 800 条投递，其中三成是投完就失联的"幽灵投递"）。项目后来还因版权顾虑移除了第三方插件。
**死因本质**：一个工具如果对生态整体是负外部性，它的口碑会先于它的技术死掉。开源尤其扛不住——维护者是免费的，骂声是免费的。

**④ JobFunnel — 死于反自动化军备竞赛**
作者归档时的说明很坦率：建于招聘站还是静态 HTML 的年代，现在各站反自动化太凶，与其假装还能用，不如存档。
**对我们的意义**：我们的 ATS 适配器是同类风险——招聘系统改一次 DOM，我们就断一次。README 里"欢迎提 PR 修 DOM 变更"这句话，本质是在承认这个维护税。

**⑤ LazyApply / AIApply — 没死，但活成了反面教材**
共同特征：定价激进（年费买断 / 按条 credits）、结果不可控（复杂表单填错、筛选题答错、跑一半崩）、退款困难。
**对我们的意义**：这一格的用户信任已经被这些产品耗光了。**我们如果用同样的话术做营销，会被默认归到同一堆里。**

**⑥ 雇主侧的反向加固（不是失败案例，是正在逼近的墙）**
- Greenhouse 的 Real Talent 主打欺诈识别与身份核验，2025-06 与 CLEAR 官宣合作，候选人在 MyGreenhouse 里自拍一张完成核验（[官方页](https://www.greenhouse.com/real-talent-candidate-matching)、[合作公告](https://www.barchart.com/story/news/32845711/clear-and-greenhouse-announce-partnership-to-enable-candidate-verification)）。
- 有来源称主流 ATS 已上线 AI 生成内容分类器、把疑似内容降权（C 级，我核不实）。
**趋势判断（这是推论，不是事实）**：投递端的门槛正在从"你能不能填完表"变成"你能不能证明你是真人且真的想来"。纯粹的填表自动化，价值在系统性缩水。

## 6. Solution（我们该怎么做得更好）

### 6.1 竞品象限

横轴：**谁点提交**（用户 ← → 机器）；纵轴：**数据在哪**（云端 ← → 用户本机）。

```
                    数据在用户本机
                          │
        career-ops        │        Mr. Weirdo Jobs（我们）
        （辅助 · 本地 ·   │        （全自动 · 本地 · 开源）
          开源 · 不点提交）│        LazyApply（全自动 · 本地 · 闭源）
                          │        AIHawk（已归档）
 用户点提交 ──────────────┼────────────────── 机器点提交
                          │
        Simplify Copilot  │        JobCopilot / LoopCV / AIApply
        LinkedIn Apply    │        Sonara / Resumly
        Assistant         │        ApplyPass（半人肉）
        Huntr / Teal      │        reverse recruiter（纯人肉）
                          │
                     数据在云端
```

**看这张图能读出三件事**：
1. 我们所在的右上格里，**闭源那家口碑塌了、开源那家归档了**——这一格目前基本是空的。空可能是机会，也可能是坟场，取决于我们能不能证明"自动提交"这件事做得比人好。
2. 左上格（career-ops）是唯一跟我们同构且活得好的。它跟我们的差别**只有最后一次点击**。
3. 右下格（云端全自动）钱最多、骂声也最多；右下角最下面那条（真人代投）钱最多、口碑最好、但完全不可规模化。

### 6.2 建议方案：把主轴从"投得多"换成"投得准 + 投得可信 + 跟得住"

**不改的（继续执行已拍板的）**：
- P1 修读数缺陷 + 跑通一轮完整投递。**理由不变而且更强了**：没有真实漏斗数据，下面所有定位讨论都是空谈。
- 每日上限 20–30 条、真跑批必须拍板人点头、不碰 LinkedIn/Indeed、相关性门控、不实内容防线——这些在调研之后**只应加强、不应放松**。

**建议新增/提前的（需拍板人拍）**：
1. **把漏斗最后一格点亮**：`confirmed_at` 全 0 必须查清是"没跑"还是"坏了"。**这是本轮调研推导出的最高优先级新发现**——它比"多投 100 条"重要得多，因为它决定我们能不能测出自己有没有用。（工程归属：需 lead 派 bug 或 builder，不是 pm 的活。）
2. **把已有的刹车讲成卖点**：README 现在第一句话讲的是"能自动提交"，这句话在 2026 年是负资产。我们真正稀缺的是"不投不相关的岗、不编造事实、不碰 LinkedIn、数据不出你的电脑、大厂配额有守卫"。
3. **降低装机门槛**（性质是分发问题，需要独立立项评估）：现状把"面向大学生"事实上缩窄成了"面向会用开发者 CLI 的大学生"。

### 6.3 取舍面（显式列出）

| 取舍 | 选哪面 | 为什么 |
|---|---|---|
| 快 vs 彻底 | **先快（P1 跑通拿数据）后彻底（重定位）** | 无数据的重定位就是拍脑袋，等于用外部传闻改自家产品 |
| 覆盖更多平台 vs 打透现有三个 | **打透现有三个** | 实测 292 个存量的 88% 在 Greenhouse，覆盖不是卡点 |
| 全自动 vs 辅助 | **暂不动，等一轮真实数据** | 砍掉自动提交等于放弃唯一差异化杠杆，且会正面撞上 career-ops |
| 讲"投得多" vs 讲"投得准" | **改讲"投得准"** | 这一条零成本、零风险，且与市场趋势同向，建议立刻改 |

## 7. Metrics（指标）

**当前主指标是错的。** 现行 PRD 的隐含主指标是"投出去多少条"（G1 = 投完存量 + 吞吐）。市场证据表明这个指标与用户真正的任务（拿到面试）之间的相关性正在崩塌。

| 类型 | 指标 | 现状 | 目标 | 测量时机 |
|---|---|---|---|---|
| **主指标** | **回复率** = 收到真实回音的投递数 ÷ 总投递数 | **测不了**（`confirmed_at` = 0，183 条历史投递零回音记录） | 第一步不是定数值，是**先把分子测出来**；拿到第一个真实分母/分子后再定目标 | P1 跑通后 30 天 |
| 次指标 1 | 批次完成率 = 一轮跑批实际投出 ÷ 该轮够格存量 | 未知（39 天没跑批） | ≥90% | 每次跑批后 |
| 次指标 2 | 每条投递的人工干预次数 | 126 条反馈里 58 次跳过、其中 24 次因表单缺信息 | 缺信息导致的跳过 → 0 | 每次跑批后 |
| **护栏 1** | 单日投递上限 | 已拍板 20–30 | 不得突破 | 每次跑批 |
| **护栏 2** | 不实内容 / 错投事件数 | 0（无记录，也可能是没在测） | 恒等于 0 | 每次跑批 |
| **护栏 3** | 平台拦截 / 账号异常事件数 | 0（无记录） | 恒等于 0 | 每次跑批 |

**三条正交的产品目标**：
- **G-A 可信**：投出去的每一条都是真的、对口的、经过刹车的。（质量维度）
- **G-B 可测**：漏斗每一格都有真数字，尤其是最后一格。（数据维度）
- **G-C 可用**：一个不是创始人的美国大学生能装上并跑完一轮。（分发维度）

三者互不包含：可信不保证可测（现在就是可信但不可测），可测不保证可用（创始人能测但同学装不上），可用不保证可信（LazyApply 极其可用，极其不可信）。

## 8. User Stories（用户故事）

**US-1｜我想知道这周有没有在推进**
> 作为一个正在找实习的大学生，我想在一次跑批之后看到"投了 N 条、其中 M 条已确认送达、K 条收到回音"，这样我才知道自己是不是在原地空转。
- ☐ 跑批结束后输出的报告包含"送达确认"与"收到回音"两格，且数字来源可追溯到本地记录
- ☐ 当某一格恒为 0 时，报告显式说明"这一格没有在测量"而不是显示 0（**当前正是 `confirmed_at` 的情况，属静默降级**）

**US-2｜我不想因为一个表单卡住整批**
> 作为用户，某个岗位的表单问了我答不上来的问题时，我希望它跳过这一条继续投下一条，并在最后一次性把这些问题问我。
- ☐ 单行缺信息只跳过该行，整批继续（已在拍板的 P2）
- ☐ 被跳过的行在报告里成组出现，问题被归纳压缩后一次性提问

**US-3｜我要确信它不会替我说假话**
> 作为用户，我需要确信这个工具永远不会以我的名义编造经历、学历或身份信息。
- ☐ 每次跑批产出的可核对记录包含"所有被填入的自述性字段来自我档案的哪一条"
- ☐ 遇到需要主观断言（法律身份、签证、GPA、成绩单、视频）的字段一律转人工，不猜（README 已声明，需在报告里可验证）

**US-4｜我要能向同学解释这东西为什么不是海投机器人**
> 作为用户，当同学问"这不就是那种乱投的机器人吗"，我要能一句话说清区别。
- ☐ README 首屏第一句话不再以"能自动提交"为主语
- ☐ 首屏包含四条边界（不碰 LinkedIn/Indeed · 数据不出本机 · 不投不相关岗 · 不编造事实）

**US-5（P2 画像，尚未验证）｜我不是学计算机的，我也想用**
> 作为非技术背景的美国大学生，我希望不用装 Node 和 Chrome 调试端口就能用上。
- ☐ **暂不设验收标准**——这条故事建立在未经访谈验证的假设上，先验证需求再谈实现

## 10. 反驳段（与现行 PRD / 已拍板优先级的冲突）

### 反驳 1（最重要）：现行 PRD 的整体主轴与市场证据相冲突

`docs/PRD-improvements.md` 的主轴是"投得出去 · 投得多 · 别老问"，G1 明写"最大杠杆 = 投完够格存量 + 吞吐 + 并行投递让大队列快速清空"。

**冲突**：这条主轴把"投递吞吐量"当作最大杠杆。而本轮调研中**唯一的 A 级效果证据**（Wonsulting 官方博客自述废弃自动投递工具的理由）直接否定了这个前提；AIHawk 归档、Sonara 倒闭、雇主侧上身份核验，三条独立线索指向同一方向。

**我不推翻已拍板的执行顺序**，理由是：读数错 14 倍是**缺陷**，缺陷必须修，跟战略无关；且不跑通一轮我们永远拿不到自己的回复率。

**但我反驳"吞吐是最大杠杆"这个判断本身。** 真正的最大杠杆是**把漏斗最后一格点亮**——183 条已投、0 条回音记录。在"有没有用"这个问题上，我们跟市场上那些被骂的产品处在完全相同的无知状态：**都不知道自己有没有用**。谁先测出来，谁就有资格谈定位。

### 反驳 2：README 与 PUBLIC_ALPHA 的对外叙事踩在跌价资产上

README 的产品描述以"Guarded auto-apply / Auto-submits"为核心卖点。市场现实是：这句话在 2026 年已经跟 LazyApply、AIApply 的差评堆在一起了。而我们真正稀缺、且**已经实现了的**四条边界（不碰 LinkedIn/Indeed、数据不出本机、相关性门控、不编造事实），全被压在 README 的"Safety Boundaries"小节里当免责声明用。

**这是一个零成本、零风险、可以立刻做的改动**：把防守写成进攻。建议 lead 排一个文案任务。

### 反驳 3：PRD 的 G4（Workday 独立 2B 轨道）应当降级更彻底

PRD 说"除非接下了金融机构合作，否则不优先"。调研支持这个判断，但还可以更狠一点：竞品的平台覆盖数（50 万企业招聘页）是**云端抓取**的产物，跟"能不能自动投递"是两码事；我们把 Workday 当成 2B 筹码去谈合作，风险是**在没跑通任何一条完整漏斗之前，先给外部承诺了一个从未实测过的能力**。建议在拿到自家真实回复率之前，不以 Workday 作为任何对外承诺的内容。

### 反驳 4：对拍板人"是不是有很多人想法跟我一样"的直接回答

有，而且比想象的多得多——但**重点不是有多少人想法一样，而是想法一样的人里已经有一批人撞墙撞回来了，并且把撞墙报告公开写在了自己的官网上**。这是我们的运气：我们不用自己去撞。

真正稀缺的、市面上几乎没人占的位置，是：**一个不替你乱投、能证明自己有没有用、数据留在你自己电脑里的学生求职工具。** 前两条我们有一半、缺一半（有刹车、无度量），第三条我们已经有了，而且是全市场最硬的差异点。

### 12.0 给拍板人的话（人话，先读这段）

**一句话**：你发来的这个项目，**不是你的竞品，是你的对照组**——它跟你想的是同一件事，但它在最后一步主动踩了刹车，而且它整个东西里**一行能跑的代码都没有**。

**第二，谁强在哪，我直说。**
- **它强在"想清楚了"**：状态怎么分、什么时候该停下问人、什么算真的投出去了、卡住之后怎么把教训变成下次的规矩——这些它都写成了明文规矩。它是一份**很好的说明书**。
- **我们强在"真的在跑"**：它 950 个岗位、183 条真实投递、一个能自己解析表单报错然后重填重交的驱动、一本去重账本、32 个测试。它那边**所有示例都是编的**（`examples/fake-demo-example/README.md:1-3` 自己写明"这是虚构的，不是真人"，`dashboard-example/application_log.csv:2` 那行备注写着"仅供演示"）。它没有任何证据表明有真人用它投出过一条。

一句更狠的话：**它是一份没被证伪过的方案，我们是一台跑过 183 次的机器。** 这两样东西谁更值钱，取决于那 183 次到底有没有换来回音——而这正是我们至今测不出来的那件事。

**第三，你该放心的和该学的。**
- **该放心**：我们不比它落后。真要论"能不能干活"，它连找岗的能力都没有（它没有任何抓岗位的机制，得靠用户自己贴链接或者靠所在的 AI 工具自己去搜，`README.md:155-161`）。
- **该学的三样（都便宜）**：① 一个**"只找岗、不投递"的首次试跑档**，让新人零风险先看一眼产品长什么样；② 岗位**新鲜度**（它默认只看 24 小时内新发的岗，`SKILL.md:46`），我们的打分里完全没有这一维；③ 它那条**"没看见确认页就不算投出去"**的记账规矩（`references/application-playbook.md:101-117`）——这条我们其实有代码在做，但报告那一头没守住，见 §12.4 回执部分。
- **该防的一样**：它建议新人**拿 LinkedIn Easy Apply 当第一次真实投递的练手场**（`README.md:185`）。这条对我们是红线，我们永远不学。

### 12.2 它有、我们没有的（逐条，不客气）

**A. 一个零风险的首次试跑档（我认为这是它最该被抄的一条）**
它的默认首跑是 **`Lead finding only`（只找岗、不投递）**：找 3-5 个岗位、分类、更新看板，**不打开任何投递流程、不点 Apply**。并且它给用户三档边界自选：只找岗 / 每次投前问我 / 只投 1-3 个低风险岗。
出处：`README.md:92-96`、`references/setup-workflow.md:51-73`、`templates/application_rules.template.md:16-24`、`SKILL.md:79`。
**我们的现状**：`README.md:46-52` 写的首跑路径是装好 → 跑主流程 → 过队列关卡 → 真投。**新用户在我们这里没有任何一档"先空跑一次看看"**。这条直接关系到"敢不敢让同学装"。

**B. 五状态收口，且每个待办都必须落在其中一个**
`Submitted`（已提交，有确认证据）/ `Skipped`（按规则跳过，带理由）/ `Blocked`（自动化卡住）/ `Needs user`（缺用户本人才有的事实或动作）/ `Pending`（值得以后再看）。这五个词在四个文件里逐字一致地重复定义。
出处：`SKILL.md:69-77`、`references/setup-workflow.md:122-128`、`templates/application_rules.template.md:96-100`、`templates/dashboard-template/README.md:34`。
**关键在 `Needs user`**：它把"缺用户的一手事实"和"网站把我们挡住了"分成两个状态。我们这边这两类混在一起（skip 理由、`essay_pending`、`stuck` 散在代码里，用户看到的是 `✅ 已投` 这类中文 emoji 标签）。

**C. 卡点 → 规矩的闭环**
每轮跑完把卡点归纳，**重复出现的卡点要变成一条写进 `automation_rules.csv`（自动化规矩表）的长期规矩**，字段含规矩内容、为什么存在、来自哪次卡点、当前是启用还是退役。
出处：`SKILL.md:81-83`、`templates/dashboard-template/README.md:93-104`。
**我们有 `feedback.jsonl`（逐条投递流水）和 `analyze_patterns.mjs`（模式分析），但没有"把重复卡点固化成会改变下次行为的规矩"这个环节。** 这是它结构上最好的一个点子。

**D. 简历分流 + 精投/海投两档**
按岗位家族（PM / 增长 / 数据 / 设计 / 工程…）各配一份简历，规定哪些头衔用哪份、哪些不用；默认海投，单个高价值岗位可以升级成精投再定制。还规定了"要定制就得给可编辑源文件（DOCX/Markdown），PDF 不适合精改"。
出处：`references/setup-workflow.md:161-217`、`templates/resume_routing.template.md:18-24`、`:60-71`。
**我们的现状**：`docs/ARCHITECTURE.md:29` 的文件清单里简历是**单数一份 `resume.pdf`**，没有按岗位家族分流，也没有任何定制机制。一个既投产品岗又投数据岗的学生，在我们这里两边发的是同一份 PDF。**这是真实能力缺口，不是叙事问题。**

**E. 岗位新鲜度作为一等筛选条件**
默认只看 **24 小时内**新发的岗，不够再放宽到 48 小时，更旧的只有匹配度特别高才碰。
出处：`SKILL.md:46`、`references/setup-workflow.md:147`、`templates/application_rules.template.md:104-108`。
**我们的打分表里六个维度（角色匹配 / 技能 / 地点 / 签证 / 层级 / 排除项，见 `shared/scoring/score_prompt.md:42-49`）没有任何一维跟"这个岗位挂出来多久了"有关。** 而我们库里的存量已经放了 41 天。

**F. 明令禁止把定性判断包装成精确分数**
原话意思是：没有外部工具给出分数时，只能用 High / Medium / Low / Stretch 这种标签，**不许假装自己算出了一个精确分**。
出处：`references/setup-workflow.md:194`。
**这条正好戳在我们身上**：我们输出 `fit_score: 7` 外加六个维度分（`shared/scoring/score_prompt.md:36-49`），并用 `fit_score >= 5` 当自动投递闸门（`.claude/skills/mrweirdo-onboard/SKILL.md:49`）。**我不认为该照搬**——批量自动化必须有个可比较的阈值，它不需要是因为每一步都有人在旁边看。**但我认为它的批评当下成立**：我们这个分数从来没有跟任何结果对照校准过（回执为 0），所以它的"精确"目前是没有依据的精确。

**G. 按宿主工具能力优雅降级**
没有浏览器工具照样能用（只做筛选、写规矩、更新看板）；有浏览器自动化就填表上传；有视觉/computer use（屏幕操作）就处理自定义下拉框和被遮挡的按钮；有邮箱工具才读验证码。
出处：`README.md:155-161`。
**我们硬要求 macOS + Node 24 + Chrome + 调试端口**（`README.md:41`、`:162-174`），少一样直接跑不起来。第一轮点出的装机门槛问题，在这里有了一个具体的反面对照：**它的装法是零运行时依赖的一句 `git clone`。**

**H. 中英双语说明书**
`README.zh-CN.md` 233 行，是英文版的完整对译而非摘要。我们是纯英文。拍板人自己是中文母语，目标人群里有相当比例的中国留学生——这是零技术成本的一条。

**I. 概念边界写成明文**
专门有一节讲清楚：候选人档案存"事实"、答案库存"话术"、规则存"决策政策"、看板存"发生过什么"，并举例说明"期望薪资"这一条在四个文件里各自该存什么。
出处：`references/setup-workflow.md:75-85`。
**我们有 `profile.json` / `search_intent.json` / `essay_profile.json` / `answer_bank.json` 四个文件，但没有任何一份文档写清楚它们的边界。**

**J. Greenhouse 邮箱验证码的逐字符操作规程**
一格一个字符地敲、敲完读回来跟邮件里的码逐字比对、对不上就停下交给用户。
出处：`references/application-playbook.md:171-180`。
**如实报告**：我在自家全仓库 grep `security code` / `verification code` / `email code`，**零命中**。我们对这个失败模式既没有代码也没有只言片语。**但我不知道我们实际是否会撞上它**（我们不登录投递，可能压根走不到那一步）——这是一个**未核实项**，交给 lead 判断是否值得让 bug 或 builder 花十分钟确认。

### 12.3 我们有、它没有的（同样逐条，不吹）

**A. 真的能跑的代码，而且不可逆的那部分是代码在管，不是话在管**
- 提交成功判定写在代码里：`shared/greenhouse_apply_driver.mjs:1277-1281`，用严格正则匹配"successfully submitted / thanks for applying"这类文案，**外加**要求落地页地址命中 `/confirmation` 且正文含特定措辞，两者取或。
- 自动投递平台白名单是代码里的一个集合：`SUPPORTED_AUTO_PLATFORMS`（受支持的自动投递平台），当前只有 greenhouse 和 ashby（`docs/ARCHITECTURE.md:53-55`）。
- 另有去重账本、批次锁、大厂配额（`README.md:99-112`）。
**它那边这些全部是 Markdown 里的句子。** 一个没照做的模型不会被任何东西拦下。**这是我们相对它最硬的一条优势，也是我建议对外讲的那一条：我们的刹车是零件，不是承诺。**

**B. 真实使用证据**
950 个岗位、183 条真实投递、292 条流水事件（`docs/active/2026-07-23_competitor-research_BUG_REPORT.md` §1 现场数据）。它那边**全部示例都是虚构的**（`examples/fake-demo-example/README.md:1-3`）。

**C. 找岗能力（这条差距最大）**
我们接了 6 个抓取源（`docs/ARCHITECTURE.md:108-118`：remoteok、greenhouse_bulk、ashby_bulk、lever_bulk、wellfound、yc_waas）。**ApplyPilot 没有任何找岗机制**——`README.md:155-161` 明写，没浏览器工具就只能筛"你给的链接"，有浏览器工具就"去搜"。**漏斗最上面那一格它整格是空的。**

**D. 跨表单的缺信息压缩提问**
我们的做法：先真投一次，解析表单自己吐出来的必填报错，能从档案或答案库补的自动补，补不上的进缺口报告，然后**一次性问最多 4 组、按"这条补上能解锁几个岗位"排序的问题，明令禁止逐个岗位列缺口、禁止用固定清单**（`.claude/skills/mrweirdo-onboard/SKILL.md:395-419`）。
它的做法：当场缺什么问什么，"问一个聚焦的问题，而不是让整页停下"（`references/setup-workflow.md:275`）。**它是逐表单问，我们是跨表单归并后问。这一条我们明显更强**，也跟项目记忆里那条原则一致（问题集必须从真实表单里推导+压缩，而非固定清单）。

**E. 去重账本**
`jobs.db` 是跨轮次的去重账本（`docs/ARCHITECTURE.md:15-17`）。它的去重是筛选规则里的一句"重复的、已关闭的、投过的就跳过"（`examples/fake-demo-example/application_rules.example.md:42`），执行方式是让 AI 去读 CSV 表核对。**到 183 行以后，靠模型读表核对必然漂移。**

**F. 回执确认这条路我们至少建了**（见下节，但请先记住：它那边连管道都没有）

**G. 不碰 LinkedIn / Indeed**
它不但碰，还把 LinkedIn Easy Apply 推荐为**第一次真实投递的最佳练手场**，理由是流程短、确认清楚（`README.md:185`），并且它的看板模板把 LinkedIn 列为头号来源（`templates/dashboard-template/README.md:20`）。
**诚实的两面**：它让人点提交，所以最后一步的风险确实低；但它的 AI 仍然在 LinkedIn 上搜索、开页、填表——按第一轮拿到的证据（LinkedIn 用户协议明文禁自动化、2023 年透明度报告把自动化列为限权首因），**这个风险照样落在学生的账号上**。我们在这条上比它干净，在最后一次点击上比它脏。**这是一笔真实的对赌，不是我们单方面更安全。**

**找不到的（如实说）**：我在它仓库里没找到任何**投递数量上限 / 频率控制 / 单公司配额**的规定（`limit|cap|per day` 全仓库 grep，命中的全是 CAPTCHA 人机验证和"低风险试投 1-3 个"这类，无一条是速率控制）。也没有任何持久化机制（除了让用户自己维护 CSV）。

### 12.4 我们卡住的四件事，它怎么处理

#### (1) 表单缺信息怎么办

| | ApplyPilot | 我们 |
|---|---|---|
| 机制 | 缺高影响事实 → 标 `Needs user`（缺用户信息）+ 进 `blocker_queue.csv`（卡点队列表）+ 当场问一个聚焦问题，不让整页停 | 先提交、解析表单自己报的错、能补的自动补、补不上的进缺口报告 → 跨岗位归并压缩后一次问 ≤4 组 |
| 高风险字段 | 工作许可 / 签证担保 / 薪资 / 自愿身份披露一律不许猜；自愿身份披露默认"不愿透露" | 法律身份 / 签证 / 成绩单 / GPA / 视频类字段转人工 |
| 出处 | `templates/answer_bank.template.md:14-20`、`templates/candidate_profile.template.json:51-58`、`references/setup-workflow.md:275` | `.claude/skills/mrweirdo-onboard/SKILL.md:395-419`、`README.md:107-108` |

**判断：这一条我们赢，而且赢得干净。** 它之所以能"当场问"，是因为人本来就坐在旁边；我们没有人坐在旁边，所以必须把问题攒起来压缩掉——这恰好逼出了更好的设计。

**但它有一样东西我们没有**：一份**用户自己拥有、自己能改**的答案库，每个问题下面写着"默认这么答"和"什么时候必须回来问我"（`templates/answer_bank.template.md:39-99`）。我们的 `shared/answer_bank.json` 在**仓库里**，是所有人共用的一份模板，里面甚至还留着针对特定公司和特定技能的硬编码条目（`shared/answer_bank.json:16-24`）。
**由此引出一个第一轮没看见的风险**：驱动层能匹配上模板的那些开放题，**所有用户填出去的话术是同一份**。同校两个学生投同一家公司，招聘方会看到近乎逐字相同的答案——这在 2026 年正好撞上"AI 生成内容识别"这条趋势线。未匹配的题会回到 AI 会话里按用户自己的档案现写（`docs/ARCHITECTURE.md:104-106`），所以风险是局部的、不是全局的，**但它是真的，且我们此前没讨论过。**

#### (2) 投递上限 / 频率怎么控

**它没有任何数值上限。** 它的节流是结构性的：每一条都要人点提交（人本身就是限速器）+ 优先低摩擦表单（不建新账号、不碰 Workday、最多一道开放题）+ 只看 24-48 小时新岗 + 首次试跑最多 1-3 条。
出处：`references/application-playbook.md:24-32`、`templates/application_rules.template.md:16-24`。

**我们**：20-30 条/天（拍板人定）+ 大厂配额 + 批次锁 + `--max` 参数。

**判断：我们赢，而且这件事值得拍板人记住一句话——"每日上限"是我们为了把人从回路里拿掉而必须补上的那块表。谁拿掉了人，谁就得装上仪表。我们装了，这是对的。**

#### (3) 回执确认怎么追踪（**本轮最重要的一问**）

它分两层，而且**两层的成色天差地别**：

**第一层：这条到底投出去了没有（提交证据）——它做得很硬**
- 正面清单：看见"Application submitted / Application sent / Thank you for applying"字样、看见致谢页、地址里含 `thanks|thank-you|submitted|confirmation`、平台状态明写已发送。
- **负面清单（这才是精髓）**：收藏的岗位、追踪器里的记录、Simplify 那类扩展打的"快速投递"标签、自动填表完成、**点了提交但没看见确认页**——一律不算。
- 记账规矩：只有确认过的才计入 `submitted_count`（已提交计数）。
出处：`references/application-playbook.md:101-117`、`references/safety-and-boundaries.md:54-58`、`templates/dashboard-template/README.md:106-113`。

**第二层：对方到底回没回（真正的回执）——它没有机制**
它有一张 `follow_up.csv`（跟进表），10 个字段，事件类型包括招聘方回信 / 拒信 / 面试 / 测评（`templates/dashboard-template/README.md:70-78`）。**这张表随包发出去是空的，全仓库没有任何一处写它怎么被填、什么时候被填、由谁填。** 它就是一张等着人手打的表格。

**对照我们（数据来自 arnold-bug 的排查报告，已实测）**：
- 第一层：我们**有代码在做**，而且逻辑跟它的正面清单几乎一样（`shared/greenhouse_apply_driver.mjs:1277-1281`），163 条投递写下了落地页地址。
- 第二层：我们**设计了自动化**（读 Gmail 带标签的邮件 → AI 抽公司岗位 → 匹配本地行 → 写入 `confirmed_at` 确认时间），但 **41 天零次触发，一条数据都没产生过**；而且取数窗口写死 7 天 / 14 天，**历史 183 条已经永远补不回来**（`docs/active/2026-07-23_competitor-research_BUG_REPORT.md` §3 根因段）。

**结论，三句话**：
1. **第一层我们领先它**——它是散文，我们是代码。
2. **第二层谁都没做出来。** ApplyPilot 不是我们要找的答案。**这不是我们独有的失败，是整个这一类产品的公共缺口**——这反而把"能测出回复率"从"补课"升级成了"可能真的是差异点"。
3. **但它有一条规矩我们该立刻抄**：它明令"没有确认证据就不许记成已提交"。我们犯的正是这条的镜像错误——报告里把"从没测过"直接印成 `confirmed_total: 0`，读起来像"我们投了 183 家、0 家回复"，实际是"我们投了 183 家、没统计过有几家回复"（`docs/active/2026-07-23_competitor-research_BUG_REPORT.md` §4 同模式风险段）。**这两句话对产品判断的影响完全相反。** 它的记账规矩正好可以当我们那条修复建议（未开启测量时显示"未开启"而不是 0）的外部佐证。

#### (4) 相关性怎么判

| | ApplyPilot | 我们 |
|---|---|---|
| 方法 | 有外部分数（Jobright / Simplify）就用；没有就定性判断，打 High/Medium/Low/Stretch 标签 | AI 会话按打分册给 0-10 分 + 六维分 + 是否推荐 + 真实性判断 |
| 用到的信号 | 头衔 / 年限层级 / 技能关键词 / 行业 / 地点与工作许可可行性 / **候选人故事连贯性** / **表单长度 vs 预期转化价值** | 角色 / 技能 / 地点 / 签证 / 层级 / 排除词，外加**最近 20 条跳过反馈注入提示词**（会学） |
| 硬闸门 | 无（人来定） | `fit_score >= 5` |
| 出处 | `references/setup-workflow.md:184-194`、`examples/fake-demo-example/application_rules.example.md:34-42` | `shared/scoring/score_prompt.md:24`、`:42-49`、`.claude/skills/mrweirdo-onboard/SKILL.md:49` |

**判断：我们的更细、而且会学（它完全不学）。但它有两个信号我们没有，且这两个都直接指向回复率：**
- **新鲜度**（岗位挂出来多久了）——早投的人被看见的概率结构性更高。
- **表单成本 vs 预期价值**——一道 30 分钟的长表单和一道 3 分钟的短表单，在"每单位精力换回多少面试"上完全不是一回事。

这两条加进打分册是**改一个 Markdown 文件的事**，我建议 lead 在 P1（修读数 + 跑通一轮）落地之后立刻排。

### 12.5 它的提示词 / 技能设计，值得偷师的（我们同为技能包，可直接比）

1. **主文件极短 + 按触发条件延后加载**：它的 `SKILL.md` 只有 90 行，正文反复出现"**当出现 X 情况时，去读 references/Y**"（`SKILL.md:30-34`、`:63`、`:87`）。我们的 `.claude/skills/mrweirdo-onboard/SKILL.md` 是 **485 行全部内联**。它这个写法把每次占用的上下文压到最小。**这是最值得抄的一条工程习惯。**
2. **状态词表就是契约**：五个状态在四个文件里**逐字一致**地重复定义，并明写"每一个岗位或尝试都必须落在这五个之一"——这是个全函数（不留未定义分支）。我们的状态散在代码和中文 emoji 标签里，没有一份权威表。
3. **正面清单旁边永远贴一张负面清单**：能力段落后面紧跟"绝不要做 / 绝不要算数"（`references/application-playbook.md:110-116`、`references/safety-and-boundaries.md:19-32`）。这是防模型漂移最便宜的写法。
4. **自动化阶梯**：浏览器自动化 → DOM 加键盘补救 → 视觉/屏幕操作 → 交还用户，并规定"先用最快且可靠的，需要时才升级"（`references/application-playbook.md:36-45`）。**我们把视觉兜底定位器扔在 `shared/sourcing/_unwired/`（未接线目录）里**（`docs/ARCHITECTURE.md:120-123`），有零件没政策——它这份阶梯正好是我们缺的那层政策。
5. **概念边界成文**（同 §12.2 I 条）：明写哪份文件存事实、哪份存话术，并给出同一个信息（薪资）在四份文件里各自的形态。
6. **一整套"假的但完整"的示例**：`examples/fake-demo-example/` 里五个状态各有一行真实长相的看板数据。它既是文档也是给模型看的样例。我们的 `examples/walkthrough.md` 是一条叙事，不是填满的成品样本。
7. **一句话安装**：把仓库链接甩给任意 coding agent 说"克隆它并用它初始化我的找活流程"（`README.md:13-17`），再配一个 `agents/openai.yaml` 给宿主界面提供显示名和默认提示语。**分发成本接近零。**

**一条明确不要学的（也是给拍板人的定心丸）**：**它的全部安全边界都是自然语言**。"永远停在提交前"这句话如果模型没照做，仓库里没有任何东西能拦住——没有测试、没有校验、没有闸门。更麻烦的是，一个纯散文的安全模型意味着**任何人提一个 PR 改一句话，就能改掉它的刹车**。我们的不可逆动作有代码闸门 + 人工关卡守着（`README.md:99-116`、`docs/ARCHITECTURE.md:53-55`）。**这一条别动。**

### 12.6 它活着吗

**事实**：单次提交，2026-06-27 "Initial ApplyPilot release"，仓库 304K（lead 克隆时记录，见本任务 TASK 档案 Round 6）。今天 2026-07-25，**28 天无更新**。作者自述这是"个人 Codex 找活流程的第一个公开版本"（`README.md:207`）。无 CI、无测试、无脚本。
**我看不到的**：star 数、issue、fork、作者其他动向——浅克隆看不到，我也没有网页抓取能力。**不编。**

**判断**：28 天不算死。一个单次提交的个人仓库，正确的读法不是"活着还是死了"，而是**"它压根还不是一个项目，它是一个人的工作方法的快照"**。拿它对标产品生命力是错的题。

**与第一轮"第 ③ 格正在死"的关系——我要在这里踩一脚刹车**：
- ApplyPilot **从来没进过第 ③ 格**，所以它既不能证实也不能证伪第一轮那个判断。
- 表面上看，现在"同形态项目里两个都主动不点提交"（career-ops、ApplyPilot），像是又一条佐证。**但这里有明显的选择偏差，我必须说出来**：拍板人是从公开可见、文档齐全的项目里找到它们的；而**替用户自动点提交的项目本来就更不倾向于公开宣传自己**——因为那正是服务条款风险所在。**"我看到的两个都不点提交"跟"市场上大家都不点提交"不是一回事。** 第一轮那批 A 级证据（Wonsulting 官方自述废弃、AIHawk 归档、Sonara 停服）依然成立且依然是主要依据；**ApplyPilot 只是一条弱佐证，不要让它把叙事夯实成"所有人都不敢点"。**

## 讨论中辩驳过的方向（被否决的方向）

**❌ 方向 A：立刻转向"纯辅助填表"，砍掉自动提交**
第一轮我确实倾向这个结论——市场证据看上去一边倒。**第二轮自己打自己**后否决：① career-ops 已经在"开源 + 本地 + CLI + 不点提交"这一格站住了，且体量比我们大两个量级，正面撞它没胜算；② 自动提交是我们目前唯一的差异化杠杆，在**没有一条自家漏斗数据**的情况下砍掉它，等于用竞品博客改自家产品——违反"不做'我觉得用户会…'判断"；③ 与已拍板的 P1 直接冲突。**结论：不砍，但改叙事、加度量，等真实数据。**

**❌ 方向 B：接 Workday / 补 5 个未接线平台，追竞品的覆盖数**
否决：实测 292 个存量的 88% 在 Greenhouse，覆盖率不是当前卡点；竞品的"50 万企业招聘页"是抓取侧数字，与投递能力无关；且与已拍板的"暂缓保留 + 挂触发条件"冲突。

**❌ 方向 C：照 LazyApply 的年费买断模式做变现**
否决：那类定价与退款纠纷高度绑定（Trustpilot 低 2 分、需走信用卡拒付），且我们零真实用户，谈定价为时过早。

**❌ 方向 D：对外叙事用"比某某更快更多"**
否决：与雇主侧趋势（身份核验、投递洪水）正面相撞，且会把我们主动归入口碑已塌的那一堆。

**❌ 方向 E：把"回复率"直接设成有数值的 KPI（比如"提到 8%"）**
否决：我们连分子都测不出来（`confirmed_at` = 0），现在定数值目标是自欺。改为"先把测量打通"。

### 第二轮新增的被否决方向（ApplyPilot 精读之后）

**❌ 方向 F：把 ApplyPilot 当竞品对标，逐条追平它的功能表**
一度成立——它文档漂亮、条理清楚，看着很像一份"我们该长成的样子"。**否决**：① 它在第 ① 格（用户自己点提交）且**没有找岗能力**（`README.md:155-161`），跟着它的功能表走等于主动搬去第 ① 格，正面撞 career-ops；② 它零可执行代码、零真实使用证据（示例全虚构，`examples/fake-demo-example/README.md:1-3`），追一份未被证伪的方案是拿我们跑过 183 次的实证去换别人的设想；③ 正确关系是**对照组**，只取可验证的单点（新鲜度、首跑空档、记账规矩）。

**❌ 方向 G：既然两个同形态项目都不点提交，我们也照做**
**否决**：这是本轮最容易犯的推理错误。① 样本只有 2 个，且**由拍板人从公开可见项目中挑出**——自动点提交的项目本就更不倾向公开宣传（服务条款风险所在），**存在明确的选择偏差**；② "永远停在提交前"是 ApplyPilot 的**产品定义**（人本来就坐在旁边），不是它测出来的安全结论，抄它等于抄一个跟我们前提不同的答案；③ 这一条属产品方向级决策，**必须拍板人拍**，pm 不替他拍；④ 与已拍板的 P1 执行顺序冲突。**结论仍是：等自家真实漏斗数据，同时把拍板人的风险偏好这个问题继续端在桌上。**

**❌ 方向 H：抄它的 CSV 看板，替换我们的 SQLite**
否决：它的 CSV 是"没有代码的项目唯一能用的存储"，不是优点。换过去会丢掉跨轮次去重账本、批次锁、并发保护——`docs/ARCHITECTURE.md:15-17`。**值得抄的是它看板里的字段设计（尤其 `follow_up.csv` 跟进表的事件类型划分），不是存储形态。**

**❌ 方向 I：用它的 High/Medium/Low 定性标签替换我们的 0-10 分**
它对"假装精确"的批评（`references/setup-workflow.md:194`）当下确实戳中我们——我们的分从没跟任何结果校准过。**但仍否决**：批量自动化必须有可比较的阈值，它不需要是因为每一步有人看着。**正确做法是先用回执数据把分数校准了，而不是把分辨率丢掉。**

**❌ 方向 J：学它拿 LinkedIn Easy Apply 做"最安全的第一次真实投递"**
否决：这是它文档里对我们最危险的一条建议（`README.md:185`）。直接违反我们的红线，且第一轮已有 A/B 级证据表明风险落在学生自己的账号上。**一秒都不考虑。**
