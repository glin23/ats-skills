### 我认为该改的三件事（按性价比）

1. **把"结果"做成一等公民**：跑完自然给出的那份总结，**数字必须由脚本算、模型只负责念**；三个数——今天投了几家 / 累计投了几家 / 有几家回了；**"没在测量"必须写成"没在测量"，不许印成 0**。现在的报告把"从没统计过"印成 `0`，读起来像"投了 183 家没人理你"——这两句话对判断的影响完全相反。

3. **首跑给一个"只找岗、不投递"的档；第一次真投明确降到 3-5 条探针**。现在新人第一次跑就是真投，而且恰好发生在档案最空的时候——学生的名字第一次出去时，答案质量是全程最差的。

### 我不同意你的一件事

**你的第 2-3 步「投递之前就把定制化问题问完」这个顺序，跟你 2026-06 自己拍的板直接冲突——而且我认为你当时是对的。**

你当时写的原话（`docs/archive/PRD-onboarding-ux.md:121-127`）：系统只有在**尝试投递的那一刻**才知道某个岗位要哪些字段，靠在浏览器里读实时表单，**没有任何"投递前就知道岗位要什么"的声明式清单**；所以"用户已决策：采用投递中收集再聚合，不做投递前探测"。

这条约束今天仍然成立（`shared/apply_batch.mjs:319-331`：空跑模式压根不打开岗位表单）。所以"投递前问完"只有两条路，两条你都提前否掉过：要么变成一张拍脑袋的固定问卷（你在同一份文件 §5.3 明令"不存在钦定的固定 N 项"），要么为了问得准，先把每个岗位的表单挨个打开读一遍（慢、脆、浏览器工作量翻倍）。

**正确的形态不是"投递前问完"，是"上一轮的真实表单，喂下一轮的前置提问"。** 你要的体感（第二次用的时候它已经懂我了）能拿到，第一次不行——第一次它必须先去撞几张表单。

**顺带两条小的**：① 你的 5 步在"投递"结束，但决定你会不会用第二次的是第 6 步（结果）；② 你的第 2 步字面写的是"针对**每个** application 需要的不同基础信息"——如果照字面做（每个岗位单独问一遍），正好撞上你自己定的反模式（`docs/archive/PRD-onboarding-ux.md:90` "禁止逐行"）。我按"最少的问题覆盖最多的岗位"来读你的意思。

## 1. Executive Summary

**一句话**：你的 5 步里，**第 4 步（画像）做得最好，第 5 步（投递）坏了，第 2-3 步（提问）做对了内核但装错了位置，第 1 步（上手）是把目标人群挡在门外的那道门**；而你最在意的"投了几家、几家回了"根本不在这 5 步里，产品里也确实没有一个能回答它的地方。

结论三句：
1. **不是功能缺失，是接线缺失。** 你要的第 2-3 步，需要的零件仓库里几乎都有——把卡点归纳成问题（已实现）、按解锁岗位数排序（已实现）、算出"哪些该提前问"（已实现，`shared/apply_gap_report.mjs:407-417`）、连存放位置都设计好了（`shared/essay_profile.template.json:79-119`）。**缺的是最后一根线：把这份清单写回档案、下次开跑时先问。**
2. **最伤上手体感的不是功能，是第一步和最后一步。** 第一步要打绝对路径 + 手动起特殊 Chrome；最后一步给你一个英文 HTML 文件的路径。中间做得再好，新人看不到。
3. **你的 5 步顺序有一处必须改**（见 §0 反驳段），改法不是推翻你的期望，是把"提问"从"投递前一次问完"改成"跨轮次越问越准"。

### 2.3 真正的问题陈述

**不是"功能不够"，是三处断裂：**

## 5. Solution

### 5.1 逐步差距分析（每步四问：做到哪 / 哪里不一样 / 缺的属哪类 / 有多伤）

---

#### 第 1 步 — 「安装了这个 Skills 之后，可以上传自己的简历」

**① 现在做到哪了（证据）**
- 装：`npx -y mrweirdo-jobs` 一条命令（`README.md:31-33`），装完会同时把技能链接进 Claude Code 与 Codex 的技能目录（`README.md:158`）。**"在 Codex 里装好就能用"这个前提成立。**
- 但硬性要求：macOS + Node 24+ + Google Chrome + Claude Code/Codex（`README.md:41`）；**首跑前还要手动跑一条命令起一个带远程调试端口的 Chrome**（`README.md:162-167`），端口被占还要换端口重来（`README.md:170-174`）。首跑脚本会在端口不通时自动帮你起（`scripts/preflight.sh:24-27`），但 Node 版本不够直接退出（`:11-15`）。
- "上传简历"的真实形态：**让用户打出一个绝对路径字符串**——技能里原话是「你要做：发我简历 PDF 的绝对路径」（`.claude/skills/mrweirdo-onboard/SKILL.md:120`），示例给的是 `/Users/you/Resume.pdf`（`:110`）。校验只认 PDF（`scripts/intake_resume.sh:18` 用 `file` 命令查类型），通过后复制到本机私有目录并设成仅本人可读（`:20-21`）。

**② 哪里不一样（做法不同）**
- **"上传" vs "打路径"**：用户脑子里的上传是拖一个文件进来。产品要的是一串路径。对不会用命令行的学生，这是第一道也是最高的一道墙。
- **只收 PDF**：Word / Google Docs 直接失败退出，没有转换、没有引导。
- **只有一份简历**：全流程共用 `resume.pdf` 一份，没有按岗位家族分流（第二轮竞品调研已记为真实能力缺口）。一个既投产品岗又投数据岗的学生，两边发的是同一份。

**③ 缺的属哪类**：**做了，但形态不同 + 环境门槛**。不是没做，也不是没接线。
**④ 有多伤**：**对新用户最伤（排名第 1）**。"没有人真正上手试过"这句话的直接原因就在这一步。

---

#### 第 2 步 — 「我们读取他的简历，并根据简历内容向他提问（比如针对每个 application 需要的不同基础信息）」

**① 现在做到哪了（证据）**
- 读简历：在主会话里直接读 PDF（`SKILL.md:170`）。✅ 做到。
- 提问：**投递之前只问 3 个固定问题**——A0 工作授权 / A1 地点 / A2 法律声明，一次性问完（`references/intake-and-profile.md:7-14`）。这三问的选择理由写得很清楚：只问"不能安全推断、否则找不对岗位"的（`:7`、`:84`）。
- **"针对每份表单要的不同基础信息"这件事真的存在，但发生在第一次真投之后**：批次跑完才生成缺口报告（`shared/apply_batch.mjs:414-421`，条件是 `if (!dryRun)`），报告读的是每一行投递的实际结果文件、只挑没成功的那些（`shared/apply_gap_report.mjs:310-333`），把表单自己吐出来的必填项报错抓出来分类。

**② 哪里不一样（做法不同——这是最容易埋雷的一条）**

### 5.2 特别核实：「问题集从真实表单反推并压缩」这条设计原则，实现到什么程度

**结论：这条原则是真的，实现了，而且实现得比我预期好——但它只覆盖了半个流程，另外半个流程里它被架空了。**

| 原则的四个子句 | 实现了吗 | 证据 |
|---|---|---|
| 问题必须**从真实表单反推**，不是拍脑袋列 | ✅ 是 | 只读真实投递结果文件里失败那些行的表单报错（`shared/apply_gap_report.mjs:310-333`），只有真跑批才生成（`shared/apply_batch.mjs:414-421`） |
| **多个原始字段压缩成少数问题**（多→少） | ✅ 是 | `shared/missing_field_questions.mjs:137-181`，且有"压缩后必须覆盖全部原始类目、漏一个抛错"的硬校验（`:174-178`） |
| **绝不逐个岗位问** | ✅ 是 | `SKILL.md:417-418` 明令"永远不要逐行列出每个岗位缺什么" |
| 按**能解锁多少岗位**排序 | ✅ 是 | `shared/missing_field_questions.mjs:114-122`，按去重后的岗位行号计数 |

**但有三个必须说清楚的限制：**

1. **"反推"决定的是"问哪几个、先问哪个"，不决定"怎么问"。** 问题的措辞是 10 条写死的中文模板（`shared/apply_gap_report.mjs:180-247`）。匹配不上任何模板的表单题，全部掉进一个兜底桶，问法是一句通用的"有表单问到了系统无法安全推断的事实，请看下面原题逐题回答"（`:241-246`）——**这一档已经退化成"把原题转发给用户"，正是这条原则想避免的东西**。
2. **分类靠的是大量手写正则匹配自由文本标签**，这个脆弱性是你自己写进 PRD 风险段的（`docs/archive/PRD-onboarding-ux.md:147`："未识别标签会落入通用桶，导致解锁数排序失真"）。**这条风险至今没有任何度量**——没人知道兜底桶里掉了多少题。
3. **它只在流程后半段生效。** 前半段（投递前）的问题集是 3 个写死的问题，**没有任何"从真实表单反推"的成分**。而你现在说的第 2-3 步，说的正是前半段。

**和你表述的一致性判断**：你说的"针对每个 application 需要的不同基础信息" + "生成定制化问题"——**内核（从真实表单来、压缩成最少）你和系统是一致的，位置（投递前 vs 投递后）不一致，粒度（因人而异 vs 因表单而异）不一致。**

### 5.3 「总结」该长什么样（承接你新拍的板：不做独立看板，做成 skill 跑完的自然输出）

#### 5.3.1 它应该包含什么

按你的原话（"今天投了几家、有几家回了"这种大白话）设计，**一屏、六行、全中文、不需要点开任何东西**：

```text
本轮完成 —— 说人话版

今天投出去      12 家     （其中 3 家是补完信息后重投成功的）
这一轮总共      12 家     累计已投 195 家
有人回你了      未开启测量  ← 不是 0，是这一格没在测（原因见下）
被卡住的        5 家      都卡在同一件事：缺永久地址（补上能解锁 5 个）
不给你投的      31 家     平台不支持 18 / 大公司名额保护 9 / 可疑岗位 4
还剩多少能投    292 家    够格、没投过、平台支持

你现在可以做一件事：回答下面 2 个问题，能再解锁 5 个岗位。
完整清单：<路径>
```

**六个数字的设计理由，一条一条说：**

| 行 | 为什么是它 | 硬要求 |
|---|---|---|
| 今天投出去 | 你原话的第一问 | 必须由脚本算、模型只念 |
| 累计已投 | 回答"我这一季在不在推进"（P1 的真实任务） | 同上 |
| **有人回你了** | 你原话的第二问 | **未测量必须写"未开启测量"，禁止显示 0**。这是本轮最重要的一条 |
| 被卡住的 + 卡在什么 | 直接连到"下一步做什么" | 必须归纳压缩后说，不许逐个岗位列 |
| 不给你投的 + 为什么 | 防"我以为它全投了"的误解（你自己写在 `docs/archive/PRD-v3.md:88`） | 分类计数，不列明细 |
| 还剩多少能投 | 这是坏掉那个读数的正面用途 | **修好之前这一行会骗人**，见依赖项 |

**必须遵守的三条铁律：**
1. **数字由脚本算，模型只负责念。** 现在的中文汇总块是模型照着几个产物自己总结的（`SKILL.md:462-485`），模型有算错和漏念的空间。总结应该是脚本吐出一段现成的文字/结构，模型原样呈现。
2. **每一格都要能回答"这个 0 是什么意思"。** 三种 0 要分开：真的是 0 / 没在测 / 没跑到那一步。现在的报告把三种混成一个 `0`。
3. **一屏结束，不给路径当主要交付。** 路径可以有，但放最后一行。

#### 5.3.2 和现有 `shared/apply_report.mjs` 的关系：**改造 + 拆一层，不是重做**

**判断：现有脚本留着，但它的定位要从"报告"降级为"存档明细"；你要的那份总结是新增的一层薄壳。** 理由：

- 现有脚本的**取数逻辑值得留**：它已经在一次查询里算好了漏斗的 9 个格子（`shared/apply_report.mjs:50-62`），包括"当前有多少可投""被大公司名额保护多少""可疑多少"。这些正是总结要用的数。
- 现有脚本的**呈现形态不该留**在主路径上：英文、HTML、只吐路径（`:89-168`）。它适合当"我想细看到底投了哪几家"的存档件，不适合当跑完的第一眼。
- **必须改的两处（都在现有脚本里）**：
  1. `confirmed_total`（`:56`、`:147`）：当回执测量从未启用时，输出必须是"未开启测量"而不是数字 0。**这一条与排障成员的修复建议、与竞品的记账规矩（"没有确认证据就不许记成已提交"）三方重合，是本项目里最便宜、最该先做的一条。**
  2. 查询里补上手动记录的进展字段（`:38-48` 的 SELECT 没有它），否则用户用 `/mrweirdo-tracker` 记的"对方回了/给了笔试/拒了"永远不会出现在任何报告里。
- **新增的那层薄壳**：把这些数字变成一段现成的中文文字，跑完直接呈现。它是不是一个新脚本、放在哪、怎么被调用——**属于架构问题，我不设计，交给 architect 与 lead。**

#### 5.3.3 在 Codex 环境里，"有几家回了"从哪来？（这是个待你拍板的问题）

现有唯一的回执来源要 Claude 的 Gmail 连接件，Codex 没有。三条路，我列出来但**不替你选**：
- **A. 手记**：你收到邮件后跟它说一句"X 公司回了"，走 `/mrweirdo-tracker` 记进去。零开发，但要你动手。
- **B. 让总结明确说"这一格没在测，想测请做 X"**：零开发，诚实，但永远测不出来。
- **C. 找一条 Codex 里也能用的读邮件方式**：需要核实可行性，我没这个能力核实。
**在你选之前，B 是必须无条件做的**——因为不管最终走哪条，"把没测的显示成 0"都是错的。

| 满足你口述的 5 步顺序 vs 守住你 2026-06 的拍板 | **守住拍板，改用"跨轮次学习"兑现你的体感** | 那条拍板背后是硬架构约束（投递前不知道表单要什么），不是偏好；硬改顺序只会变成固定问卷，正是你明令禁止的 |

| 总结做全（漂亮完整）vs 做小（六行说人话） | **做小** | 你的原话就是"今天投了几家、有几家回了"；做大会重新滑向被你否掉的"独立看板" |

| 报告全推倒重做 vs 改造现有 | **改造 + 加薄壳** | 现有取数逻辑是对的，坏的是呈现层和两个字段的语义 |

## 6. Metrics

**主指标要换。** 上一轮我建议主指标从"投递条数"换成"回复率"，那条仍然成立但**现在还测不了**。本轮盘点的主题是上手体感，所以本轮主指标是：

| 类型 | 指标 | 现状 | 目标 | 测量时机 |
|---|---|---|---|---|
| **主指标** | **首跑完成率** = 一个**非创始人**的美国大学生，从装到成功投出第一条、全程无维护者介入的比例 | **0 / 0**（至今零个非创始人用户跑过，拍板人原话"可能也没有人真正上手试过"） | 邀请 3-5 人，**≥3 人跑通** | 存量投递跑通 + 上手体感三件事落地后 |
| 次指标 1 | **从装好到看见第一个岗位**需要用户动手几次 | 至少 3 次（起 Chrome 的命令、打绝对路径、队列关卡回"开始"），**未实测** | ≤2 次，且**不含任何需要打路径/命令的动作** | 每次改上手流程后 |
| 次指标 2 | **第二轮开场时，系统已经知道的用户事实条数** | **0**（跨轮次学习完全没接线） | 第二轮开场问的问题 ≥50% 来自上一轮真实表单卡点 | 接上"卡点→前置问题"之后 |
| 次指标 3 | 每轮被问的问题数 ÷ 因此解锁的岗位数 | 未测量 | 越低越好，先建立基线 | 每次跑批后 |
| **护栏 1** | 单日投递上限 | 已拍板 20-30 | 不得突破。**注意：终端看板里写死的是 50**（`scripts/dashboard.mjs:35`），与拍板不一致，需核实是否只是显示 | 每次跑批 |
| **护栏 2** | 以用户名义做出的**未经确认的事实陈述**数 | **未知，且代码里有已知洞**（§9 第 3 条） | 恒等于 0 | 每次跑批 |
| **护栏 3（新增）** | 报告里**把"未测量"显示成 0** 的格子数 | 目前 ≥1（回执那一格） | 恒等于 0 | 每次出报告 |

**三条正交的产品目标（本轮版本）**：
- **G-可用**：一个不是创始人的学生能装上、跑完、看懂。（分发维度）
- **G-可信**：投出去的每一条，里面的每一句话都能追到用户自己说过的事实。（质量维度）
- **G-可见**：跑完能用一句人话说清发生了什么、下一步做什么。（反馈维度）

三者互不包含：现在的产品**可信度中等偏高、可用性最低、可见性最低**。可用不保证可信（LazyApply 极其可用、极其不可信）；可信不保证可见（我们现在就是刹车硬、结果看不见）。

## 7. User Stories

**US-1｜我要能像发文件一样把简历交给它**
> 作为一个不写代码的大学生，我想把简历给它的时候不用知道什么叫"绝对路径"。
- ☐ 首跑提示里不再以"绝对路径"作为唯一说法，给出至少一种不需要用户理解路径概念的做法
- ☐ 非 PDF 文件（Word / 网页文档）给出可执行的下一步，而不是直接失败退出
- ☐ `README.md` 与 `docs/PUBLIC_ALPHA.md` 里"需要一段简短自我介绍"的说法与技能实际行为一致（技能里早已改为可选）

**US-2｜我要它记得上次卡在哪，别让我每次重来**
> 作为用过一次的用户，我希望第二次跑的时候，它开场就问上次真正卡住我的那几件事，而不是又从头三问开始。
- ☐ 上一轮缺口报告里算出的"重复出现、值得前置"的字段（`shared/apply_gap_report.mjs:407-417` 已经在算），写进这个用户自己的档案
- ☐ 下一轮开场时，这些字段作为一次性提问出现，且仍遵守"压缩后再问、按解锁岗位数排序、不逐个岗位列"
- ☐ 已经答过的事实不再重问（现有机制已支持：答案写进档案后自动改判为"系统能填"）

**US-3｜我要跑完就知道发生了什么，不用去开一个网页**
> 作为用户，跑完之后我想直接看到"今天投了几家、几家回了、还剩多少能投、下一步做什么"。
- ☐ 跑完的最后一屏是中文人话总结，六行以内，路径放最后
- ☐ 总结里的数字由脚本产出，模型不重新计算
- ☐ **任何一格没在测量时，显示"未开启测量"，禁止显示 0**
- ☐ 用户手动记录的进展（对方回复 / 笔试 / 面试 / 拒信）出现在总结里

**US-4｜我要确信它不会替我说我没说过的话**
> 作为用户，我需要确信它在表单上填的每一条关于我的事实，都来自我自己给过的信息。
- ☐ 工作授权、学位、退伍军人身份这三类问题，在档案里没有明确值时**不得使用共用默认答案**（现状见 §9 第 3 条）
- ☐ 薪资期望在档案为空时，不得用一句共用话术顶上（现状 `shared/answer_bank.json:146`）
- ☐ 每轮总结里可以看到"本轮有 N 条回答来自你亲口给的事实、M 条来自系统默认"

**US-5｜我要先看它长什么样，再决定要不要真投**
> 作为第一次用的人，我想先让它只找岗位、不投递，看看它找的岗位对不对，再决定要不要放它去投。
- ☐ 首跑提供"只找岗、不投递"的选项（现有空跑能力已存在于 `shared/apply_supervisor.mjs --dry-run`，但没有作为用户可选项暴露）
- ☐ 第一次真投默认是小批探针（3-5 条），不是满批
- ☐ 队列关卡的语义、身份复核块、"开始"确认一个字不动

## 8. Out of Scope / Dependencies / Risks / Open Questions

### Out of Scope（本轮明确不做，每项附理由）

1. **不写任何代码、不改任何代码文件** — 任务边界，且本轮无施工授权。
2. **不做目录结构与模块划分** — architect 正在并行做同一主题的架构侧盘点，重复即冲突。
3. **不推翻"投递中收集再聚合、不做投递前探测"这条决策** — 那是拍板人 2026-06 的决策，我在 §0 反驳段解释了为什么我支持它；要推翻必须他自己推。
4. **不救历史 183 条投递** — 已拍板（2026-07-23 关卡 2 决策）。
5. **不做独立看板** — 已拍板（本任务第 1 轮）。
6. **不接 Workday / iCIMS / 5 个未接线平台** — 已拍板暂缓挂触发条件；存量 88% 在已支持平台，覆盖不是卡点。
7. **不做定价、不做获客入口物** — 连一个非创始人用户都还没有，谈这些是伪问题。
8. **不重排已拍板的三件事优先级** — 修读数 + 跑通一轮仍是第一优先；本文所有建议都排在它后面或与它并行。

### Dependencies（依赖）

- **"还剩多少能投"这一行必须等读数缺陷修完才准**，否则新总结会用一个漂亮的形式重复报错数字（现在低报约 14 倍）。

- **主指标（首跑完成率）依赖真实的非创始人用户**，这是连续三轮未被填补的缺口。

### Risks（风险）

| 风险 | 影响 | 判断依据 |
|---|---|---|
| **以用户名义做出未经确认的事实陈述** | 最严重且不可逆——投出去的是学生的名字 | `shared/answer_routing.mjs:178-180`、`shared/greenhouse_apply_driver.mjs:1569-1570`、`shared/ashby_apply_driver.mjs:512` 三处代码 |

### Open Questions（待解问题，必须回答的在前）

1. **第一批"探针"投递怎么定？** 3-5 条小批，还是直接跑满 20-30？**这是对外不可逆动作，必须你拍。**
2. **工作授权 / 学位 / 退伍军人身份的共用默认答案，算不算"编造"？** 你给一个明确判定，我们才知道要不要改驱动（改法属架构与排障，不属我）。
3. **在 Codex 环境里，"有几家回了"走 A（你手记）/ B（诚实说没在测）/ C（另找路子）哪条？**
4. **"结合简历生成定制化问题"这件事，你要到什么程度？** 是"问简历里没写但表单常要的事实"（便宜，接线即可），还是"读出简历里的空档期/项目细节来追问"（新能力，要新设计）？

6. **上手门槛降到什么程度算够？** 这决定"面向所有美国大学生"是定位还是口号——也决定要不要为此单独立项。

## 9. 用户写过、但没被实现 / 已被悄悄改掉的需求

> **说明**：以下"原文摘录"中的旧用词已按项目术语表统一（岗位 / 投递），语义未改。出处为仓库内实际文件行号。**这一节是本轮任务里你最担心被漏掉的部分，所以我把能找到的都列了，包括已经兑现的（标 ✅），免得你以为我只挑坏的说。**

### ❌ 一、"卡住的字段要沉淀成前置问题、批量提前问"——一行都没接

  **出处**：`docs/archive/HANDOFF-v2.2.0.md:332-339`
- **原文摘录 2**：「onboard 应当把任何 'unknown' 字段**提前（批量）呈现给用户**，这样自动投递循环就不会在中途卡住。」
  **出处**：`shared/essay_profile.template.json:80-83`

- **为什么这条最重要**：**它就是你现在说的第 2 步和第 3 步。** 你 2026-06 就写下来了，写了两遍，41 天没接。

### ❌ 二、"薪资期望改成问用户"——从没加过这一问，还被静默改成了系统自己答

- **原文摘录**：「A0/A1/A2 三个硬边界问题已在第 1 步；**A3 薪资 = 加一问**。」「`work_authorization.salary_expectation_usd` 字段已存在于 `shared/profile.template.json`。」「薪资改为『用户提供』已规避（truthfulness 风险）。」
  **出处**：`docs/archive/PRD-onboarding-ux.md:137-138`、`:148`
- **现状**：三处都没落地。
  - 硬边界问题至今是 A0/A1/A2 三个，**没有 A3**（`references/intake-and-profile.md:10-14`）。
  - 字段确实存在但永远是空字符串（`shared/profile.template.json:44`）。
  - 三个驱动都读它，读到空就回落到一句**全体用户共用的话术**："Open to discussion based on the role, location, and the company's standard internship or entry-level range."（`shared/answer_bank.json:146`；使用处 `shared/greenhouse_apply_driver.mjs:1698`、`shared/lever_apply_driver.mjs:257`）。

- **判断**：这是"写过 → 没做 → 而且被一个默认值悄悄替代了"的完整案例。

### ❌ 三、"绝不编造个人事实"这条红线，在代码里有三个洞

- **原文摘录**：「**绝不编造个人信息。** 未知的事实保持空值，或者变成'问/跳过'的阻塞项。」（`references/intake-and-profile.md:45`）
  「不编造底线（任何新路径不得旁路）：**工作授权 / GPA / 人口统计 / 法律声明 / 背景调查 / 搬迁 / 薪资接受度只能来自显式问答**。」（`docs/archive/PRD-v3.md:86`、`:230`）
